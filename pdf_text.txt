01   Project Overview 
 
Project LOOP is a corporate-grade web application that helps companies make sense of the 
customer feedback they receive every day. Support tickets, app-store reviews, survey 
responses, and sales notes pile up faster than any team can read them. LOOP ingests that 
feedback, uses AI to classify and cluster it, surfaces what is trending, and answers plain-English 
questions about what customers actually want. 
You are building the kind of internal product that real SaaS companies pay for — comparable in 
spirit to tools like Enterpret, Dovetail, or Productboard Insights. It is deliberately not a to-do app or a 
basic blog with a chatbot bolted on. It forces you to handle the things you would actually own as a 
junior engineer at a product company: multi-tenant data, role-based access, a clean API layer, a real 
database, a charts dashboard, and AI features that require genuine understanding to implement.

Why this project was chosen for you 
Portfolio value — “I built a multi-tenant AI feedback-intelligence platform” is a sentence that gets 
interviews. It demonstrates full-stack ownership, not a tutorial clone. 
Hard to fake — tenant isolation, RBAC, and retrieval-grounded AI cannot be copy-pasted from a single 
YouTube video. Your understanding will show in the build. 
Measurable — the feature set maps cleanly onto Zidio’s scoring rubric, so your grade reflects what you 
shipped, not opinion.

02   Business Context & Problem Statement 
 
2.1  The problem 
Every product company is drowning in customer feedback that arrives through too many doors at 
once. A typical mid-size SaaS company might receive feedback through all of the following in a 
single week: 
• Support tickets and live-chat transcripts. 
• App-store and review-site ratings with written comments. 
• NPS and CSAT survey free-text responses. 
• Sales and success call notes (“the customer asked for X again”). 
• Social mentions and community posts. 
Individually each item is a sentence or two. Collectively they hold the answer to the most valuable 
question a company can ask — “what should we build, fix, or improve next?” — but no human has 
time to read, tag, and synthesise hundreds of items a week. So the feedback rots in spreadsheets 
and inboxes, and product decisions get made on gut feel and the loudest voice in the room. 
2.2  The opportunity 
LOOP closes that gap. It is the single place a team drops all of its feedback, and the AI does the 
reading: it tags every item, groups similar items into themes, flags what is spiking this week, and lets 
anyone ask questions in plain English and get answers grounded in the actual feedback. The team 
goes from “we think customers want this” to “43 customers asked for this in the last 30 days, and 
complaints about it are up 60% week-over-week.” 
Your business framing for the demo 
When you present LOOP, frame it as a product, not a class assignment. Imagine you are pitching it to a 
Head of Product who has 90 seconds. The headline is: “LOOP turns scattered customer feedback into a 
ranked, evidence-backed list of what to do next.” Build and demo with that sentence in mind.

06   System Architecture 
 
LOOP follows a standard three-tier architecture. The browser talks only to your own API layer; the 
API layer is the only thing that talks to the database and to the Claude API. Never call the AI 
provider directly from the browser — your API key must stay server-side. 
6.1  Request flow 
1. The browser (React Server/Client Components) renders the UI and calls your API route 
handlers. 
2. Route handlers authenticate the session, check the user’s role, and scope every query to the 
caller’s workspace. 
3. Prisma reads/writes PostgreSQL. All feedback rows carry a workspaceId; queries always filter 
on it. 
4. For AI features, the route handler builds a prompt, calls the Claude API server-side, parses the 
response, and returns clean JSON to the browser. 
5. For Ask LOOP, the handler first retrieves the most relevant feedback (vector search), then 
passes it to Claude as grounding context before answering.

08   Feature Specification 
 
Each feature below has a user story and acceptance criteria. Acceptance criteria are how mentors 
decide whether a feature “counts.” Treat them as your definition of done. Features are grouped into 
Core (the application) and AI (the intelligence). 
8.1  Core features 
C1   Authentication & workspaces 
User story:  As a new user, I can create an account and a workspace, then log in securely so my company’s 
data is private. 
Acceptance criteria 
1. Sign-up creates a User and a Workspace; the creator becomes ADMIN. 
2. Passwords are hashed; sessions persist across refresh. 
3. Logged-out users are redirected away from protected pages. 
4. All data the user sees is scoped to their workspace only. 
 
C2   Role-based access control 
User story:  As an admin, I can invite teammates and assign roles so people only do what their role permits. 
Acceptance criteria 
1. Three roles exist: ADMIN, ANALYST, VIEWER. 
2. Admins manage members and roles; Analysts ingest and manage feedback; Viewers are read-only. 
3. The API enforces roles server-side — hiding a button is not enough. 
4. Attempting a forbidden action returns 403, not a crash.

8.2  AI features 
These four features are the heart of LOOP and the heaviest-weighted part of the grade. Each must 
work end-to-end against real seeded data in your demo. 
AI1   Auto-classification 
User story:  As an analyst, every piece of feedback is automatically tagged so I never have to triage by hand. 
Acceptance criteria 
1. On ingestion, each item is sent to Claude and returned with: sentiment, sentiment score, theme(s), and a short 
feature-area label. 
2. Output is strictly structured (JSON) and validated before saving. 
3. Classification is stored on the record — not recomputed on every page load. 
4. A manual “re-classify” action exists for corrections. 
 
AI2   Theme clustering & trends 
User story:  As a product manager, I can see which themes are growing so I can react to emerging issues early. 
Acceptance criteria 
1. Similar feedback is grouped into named themes with counts. 
2. A trends view shows theme volume over time and flags themes spiking versus the previous period. 
3. Clicking a theme drills into the underlying feedback items. 
4. New feedback is assigned to existing themes where it fits, or forms a new one.

AI3   Ask LOOP (grounded Q&A) 
User story:  As anyone on the team, I can ask plain-English questions and get answers backed by real feedback. 
Acceptance criteria 
1. A chat-style box accepts questions like “What are users saying about onboarding?” 
2. The system retrieves the most relevant feedback (semantic search) before answering. 
3. Answers cite or list the specific feedback items they are based on. 
4. The model must not invent feedback that is not in the data — grounding is mandatory. 
 
AI4   Voice-of-Customer report 
User story:  As a product manager, I can generate a weekly digest I could forward to leadership without editing. 
Acceptance criteria 
1. One click generates a report for a chosen period. 
2. The report summarises top themes, sentiment shifts, notable verbatim quotes, and recommended actions. 
3. Reports are saved and viewable later, and exportable (PDF or shareable page). 
4. Content is generated from the period’s actual data, not generic filler. 
09   AI Implementation Notes 
 
This section gives you a starting approach for each AI feature. You are expected to refine the 
prompts yourself — prompt design is part of the learning and part of the grade. 
9.1  Structured classification (AI1) 
Ask Claude to return JSON only, with a fixed schema, and validate it with Zod before saving. A 
robust approach: 
• Send the feedback text plus your list of existing theme names so the model reuses themes 
instead of inventing new ones each time. 
• Instruct the model to return only JSON: sentiment, sentimentScore (-1 to 1), themes (array), 
featureArea, and a one-line rationale. 
• Strip any stray markdown fences, parse, validate, and fall back gracefully if parsing fails (retry 
once, then flag for manual review). 
9.2  Retrieval-grounded Q&A (AI3) 
Ask LOOP must answer from the data, not from the model’s imagination. The pattern is retrieve-
then-answer: 
1. Embed every feedback item when it is ingested; store the vector (pgvector or a vectors table). 
2. On a question, embed the question, find the top-K most similar feedback items. 
3. Pass those items to Claude as context with an instruction: answer only from the provided 
feedback; if the answer is not present, say so. 
4. Return the answer plus the list of feedback items it used, so the user can verify it.

9.3  Report generation (AI4) 
Pre-compute the period’s stats (top themes, counts, sentiment deltas, a few representative quotes) 
in code, then ask Claude to write the narrative around those numbers. This keeps the report 
accurate and cheap, and stops the model from hallucinating figures. 
Cost, safety, and keys 
Keep your API key server-side only. Never ship it to the browser or commit it to Git. Use environment 
variables. 
Be economical. Classify on ingest and cache results; do not call the model on every page render. Batch 
where you can.

14.1  Prerequisites 
• Node.js 18 LTS or newer, and Git. 
• A free PostgreSQL database (Neon or Supabase). 
• An Anthropic API key (your mentor will advise how to obtain credits). 
• A Vercel account connected to your GitHub. 
14.2  First-run steps 
# 1. Create the app and install dependencies 
npx create-next-app@latest loop --typescript --tailwind --app 
cd loop && npm install prisma @prisma/client next-auth zod recharts 
npm install @anthropic-ai/sdk 
 
# 2. Configure environment variables (never commit this file) 
#    .env  ->  DATABASE_URL, NEXTAUTH_SECRET, ANTHROPIC_API_KEY 
 
# 3. Set up the database 
npx prisma migrate dev --name init 
npm run seed 
 
# 4. Run locally, then deploy 
npm run dev      # http://localhost:3000 
vercel           # production deploy 
 
Environment variables 
Keep ANTHROPIC_API_KEY, DATABASE_URL, and NEXTAUTH_SECRET in .env locally and in Vercel’s 
project settings for production. Add .env to .gitignore on commit one. A leaked key is a security incident and 
an automatic deduction. 
15   Coding Standards & Git Workflow 
 
You are graded partly on how you work, not just what you build. Treat this repo as if a teammate will 
inherit it. 
15.1  Code quality 
• TypeScript everywhere; avoid “any”. Let types document your data. 
• Validate every API input with Zod; never trust client data. 
• Keep business logic out of components — put it in API routes / service files. 
• Handle errors explicitly; show users a friendly message, log the detail. 
• Consistent formatting (Prettier) and linting (ESLint). 
15.2  Git workflow 
• Commit early and often with meaningful messages (e.g., “feat: add CSV ingestion with row 
validation”).

16   Suggested Repository Structure 
 
A clean structure makes your project easy to grade and easy to extend. This is a recommended 
starting layout for the Next.js stack. 
loop/ 
  app/ 
    (auth)/login, signup 
    (app)/dashboard, inbox, trends, ask, reports, settings 
    api/ 
      auth/...        # NextAuth 
      feedback/       # CRUD + ingestion 
      themes/         # clustering + trends 
      insights/       # Ask LOOP Q&A 
      reports/        # VoC generation 
  components/         # UI building blocks (charts, tables, forms) 
  lib/ 
    ai.ts             # Claude calls: classify, answer, report 
    search.ts         # embeddings + retrieval 
    auth.ts           # session + role guards 
    db.ts             # Prisma client 
  prisma/ 
    schema.prisma 
    seed.ts 
  README.md 
  .env.example        # documented, no real secrets

The one rule of asking for help 
Come with what you tried. “My CSV import throws this error, here’s the code and what I’ve already 
checked” gets a fast, useful answer. “It doesn’t work” does not. Showing your working is itself a graded 
professional skill. 
18   Originality & Academic Integrity 
 
This project is designed to be built, not copied. Originality is a condition of certification. 
• You may use AI coding assistants and documentation — that is modern engineering. You must 
understand and be able to explain every line you submit. 
• You may reference tutorials and starter templates, but the LOOP feature set, data model, and 
AI logic must be your own implementation. 
• Directly copying another intern’s repository, or submitting a purchased/cloned project, results in 
disqualification. 
• At your final review, mentors may ask you to explain or modify any part of your code live. Be 
ready to.

21   Appendix C — Glossary 
 
Term Meaning 
Multi-tenant One application serving many isolated customers (“tenants”); each tenant’s data 
is private. 
RBAC Role-Based Access Control — permissions determined by a user’s role. 
Tenant isolation Guaranteeing one customer can never read or write another customer’s data. 
Embedding A numeric vector representing text meaning, used for semantic similarity search. 
RAG Retrieval-Augmented Generation — fetch relevant data first, then let the model 
answer from it. 
Grounding Forcing the AI to answer only from provided data, not from memory or invention. 
VoC Voice of Customer — the synthesised view of what customers are saying. 
Seed data Sample records loaded into the database so the app is usable and demoable 
immediately.
